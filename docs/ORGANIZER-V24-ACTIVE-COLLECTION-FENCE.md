# V24 — межі захисту активної колекції під час Undo

Дата: 2026-10-17. База: консолідована V23. Ця зміна не змінює міграції SQLite.

## Відтворений дефект у V23

`UndoLibraryOrganizationUseCase.undo` перевіряв належність журналу до активної колекції тільки один раз, до завантаження елементів. Якщо контекст колекції змінювався під час отримання `journal.items(operationId)` або після відкату одного елемента, наступний файл міг бути змінений без повторної перевірки колекції. Два регресійні JUnit-тести, які примусово змінюють активний ID на цих межах, на незміненій реалізації V23 очікувано падали.

## Пом'якшення

Після перевірки авторитетного `OrganizationJournalOperation.collectionId` зафіксований ID зберігається на час Undo. Активна колекція повторно перевіряється після завантаження списку, перед кожним елементом, після файлового відкату, перед записом стану елемента й перед фінальним оновленням операції. Якщо ID змінився, відкат припиняється. Успішно записані в журналі стани `ROLLED_BACK` дозволяють повторному виклику не обробляти вже завершені елементи.

Стандартні перемикання колекцій також мають координуватися через `LibraryOperationCoordinator`, але додаткові перевірки захищають від помилок нестандартних і застарілих інтеграцій.

## Обмеження

- Перевірка ID є *best effort*, а не атомарним mutex на `CollectionLifecyclePort`, файловій системі та SQLite. Перемикання або збій **усередині** блокувального файлового I/O лишається можливим.
- Після завершеного файлового кроку і до оновлення SQLite-журналу може залишитися частково виконаний відкат. Потрібні повторний запуск, перевірка хешів та ручне примирення за сумнівів.
- Немає приймальних тестів Windows/NTFS/UNC/DPAPI, і немає даних реального зависання першої книги.
- Тести V24 використовують штучну зміну ID і тимчасові файли; вони не моделюють реальне перепідключення SQLite або фізичне вимкнення живлення.

Заборонено оголошувати цю зміну повним crash-consistency чи Windows production sign-off.

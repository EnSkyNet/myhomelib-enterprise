# MyHomeLib Enterprise 8.0.0 R18 — консолідований цикл V7

**Стан:** кандидат для розширеного приймання, **не production-ready**.

**Основа:** `MyHomeLib-Enterprise-8.0.0-R18-CONSOLIDATED-AUDIT-2026-10-16-SOURCE-V6.zip`.
Усі дії проводилися над окремою копією вихідного коду, тестовими тимчасовими файлами та синтетичними SQLite-базами. Реальні `D:\Flib\Flib.db`, `D:\Другие` й особисті файли не відкривалися і не змінювалися.

## 1. Підтверджені проблеми і виправлення

| ID | Ризик | Причина у V6 | Зміна V7 | Перевірка |
|---|---|---|---|---|
| R18-V7-01 | Скасування організатора не зупиняло великого копіювання до його завершення | `NoLinkPathSafety.copyFreshFile` не приймав і не перевіряв сигнал скасування між блоками | Перевірка сигналу та переривання потоку між блоками; контрольована очистка лише власного неповного файла | Реальні Java copy smoke + JUnit-регресії |
| R18-V7-02 | На FAT/exFAT/деяких мережевих томах fallback-публікація виконувала некероване `Files.copy` | Відсутній cancellation-aware шлях після недоступного hardlink | Обмежений 1 МіБ буфер, `CREATE_NEW`, перевірка шляхів, скасування та власності неповного файла | Java тест із навмисним `Operation not supported`; JUnit додано |
| R18-V7-03 | Скасування під час формування цільового файла могло не перевірятися у Publisher | `OrganizerTargetPublisher` не приймав cancellation supplier | Передача сигналу через перевірку, копіювання, перевірку SHA-256 та після фінального хешування; без зміни каталогу при помилці | Java publication smoke + JUnit-регресії |
| R18-V7-04 | Відсутність ознак прогресу під час довгого копіювання/хешування першої книги | Сигнали діагностики лише до/після операції | Лог `FILE_COPY_PROGRESS` та `ORGANIZER_HASH_PROGRESS` щонайменше раз на 5 с активної роботи, із кількістю оброблених байтів | Збірка реальних класів; контракт і код-рев'ю |
| R18-V7-05 | Відсутність наскрізного тесту всіх SQL-міграцій | Попередні тести переважно використовували спрощену V70-подібну схему | Автоматичні Python-тести реальних SQL-файлів V1–V71, оновлення справжньої схеми V70 та відкату V71 за SQL-помилки | 3 нові Python-тести PASS |

**Обмеження реалізації:** скасування кооперативне, після завершення поточної файлової операції введення/виведення; воно **не може примусово перервати** завислий системний виклик, диск або SMB-запит. Fallback без hardlink не є атомарним з погляду спостерігачів: незавершений файл може бути тимчасово видимим, а каталог змінюється тільки після перевірки SHA-256. Ризик вимкнення живлення перед `fsync`/durability бар'єром залишається.

## 2. Перевірки в цьому циклі

- Встановлений Java 21: компіляція п'яти змінених справжніх production-класів через `javac` — **PASS**.
- `python -W error::ResourceWarning -m unittest discover -s tools/tests -p 'test_*.py' -q` — **86 тестів, OK**, зокрема JDK smoke, V1–V71 та ін'єкція аварійного відкату.
- `python tools/organizer-copy-jdk-smoke.py` — **PASS, 12 + 7 тверджень**, перевірено байти, скасування, колізії, fallback та захист оригіналу.
- `python tools/static_release_check.py` — **PASS**: 51 XML, 30 FXML workspace, 275 references, 71 міграція, integrity=ok, статичні перевірки скриптів і пакування.
- Maven **3.9.16 / JDK 21** доступні; офлайн `xvfb-run -a mvn -B -ntp -o -Pproduction clean verify` завершується `exit 1` **до компіляції** через відсутні POM `org.springframework.boot:spring-boot-dependencies:4.1.1` та `org.openjfx:javafx:21.0.12`. Це не є доказом помилки у вихідному коді; Java/JUnit-збірка всіх модулів не підтверджена.
- Окремий старий `tools/v71-standalone-java-smoke.py` у цьому середовищі не завершився в межах допустимого прогону; не позначено PASS.

## 3. Відкриті production-блокери

1. **P0** — повне Maven `-Pproduction clean verify` з доступними залежностями, усі тести (включно з новими JUnit) — PASS; зберегти `surefire/failsafe` evidence.
2. **P0** — Windows 10/11 і NTFS/SMB/exFAT на **копії** бібліотеки: перша книга, скасування на різних етапах, колізії з різним регістром, довгі імена, ACL/антивірусні блокування, пошкоджені journaling файли, повторний запуск. Перевірка recovery до/після підтвердження SQLite, фізичних файлів, SHA-256.
3. **P0** — Flyway V71 на тестовій копії існуючої БД, `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, snapshot/WAL, backup/restore, дві незалежні позиції та відкат після помилки. Тест Python перевіряє SQL, а не конфігурацію Flyway/JDBC/профіль production.
4. **P0** — гарантії багатопроцесного доступу до журналів Reader, а також захист від старіших синхронізацій/записів інших пристроїв. Нові стовпці V71 незалежні, але загальні `percent`, `updated_at` та `anchor_id` залишаються last-active.
5. **P1** — JFR та профілювання heap на копії бібліотеки масштабу 596 тис. книг: JavaFX FX-thread, Lucene, SQLite, кеші, bounded queues, цикл індексації/очищення.
6. **P1** — Windows installer/portable smoke з журналами, відкатом та контрольними сумами.

## 4. Послідовність приймання на Windows без ризику для оригіналу

- Створити окрему тестову копію БД, фізичних файлів, журналів і резервну копію цієї копії; відкрити лише тестову колекцію. Перевірити hashes до/після.
- Виконати `tools\\invoke-maven.cmd -B -ntp -Pproduction clean verify` або стандартний `mvn -B -ntp -Pproduction clean verify` на JDK 21 і Maven >=3.9.6 з доступом до залежностей.
- Завантажити пробну копію, перевірити text/audio resume після crash/close/restart; виконати preview організатора.
- На копії: застосування до 1–10 папок, скасування під час `STAGING`, `PUBLISH`, `CATALOG`, `SOURCE_REMOVE`; перевірити фізичні файли, `book_artifacts`/`books`, журнали й recovery. Відкрити й перевірити книги.
- Повторити без зміни оригінального каталогу; не запускати масове упорядкування до повного PASS.

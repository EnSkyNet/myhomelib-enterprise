## Знайдені проблеми та виправлення

### 1. EPUB: зайвий багатократний пошук записів ZIP

**Код:** `myhomelib-infrastructure/.../content/EpubContentExtractor.java`.

Раніше, коли регістр символів у шляху ресурсу з OPF не збігався з ZIP, `findEntry()` для кожного розділу проходив усі записи ZIP. Для `N` розділів і `M` записів це потенційно O(N×M) перевірок назв. Замінив на одноразову перевірку та індексацію ZIP: окремі мапи для точних і безрегістрових назв; перевагу точного збігу збережено. Всі ліміти й перевірки небезпечних ZIP-записів залишені.

**Нові тести:** 240 розділів із різним регістром шляхів; точний збіг має пріоритет над безрегістровим. Приріст швидкості для реальної бібліотеки **не виміряно**; підтверджено лише усунення повторних повних проходів.

### 2. Відновлення: залишковий тимчасовий SQLite-файл після невдалої перевірки

**Код:** `myhomelib-application/.../service/BackupRestoreService.java`.

У `installDatabaseCandidate()` очищення файлу `.restore.tmp` раніше знаходилося тільки у блоці `finally` навколо самої заміни БД. Якщо `validateDatabaseFile()` або перевірка SHA-256 завершувалися до цього блоку, етап відновлення завершувався із залишковим файлом; наступна спроба отримувала помилку «staged Restore database already exists».

Тепер очищення перевіреної staging-копії виконується зовнішнім `finally`, який охоплює й попередню перевірку. Видалення відбувається **лише після підтвердження володіння за SHA-256**; невідома або підмінена копія зберігається як доказ для безпечного відновлення. Активна база перед перевіркою не закривається.

**Нові тести:** після помилки перевірки тимчасового файлу немає, активна база незмінна; повторна спроба проходить. За помилки під час запису до обчислення хешу неперевірену часткову копію поки збережено задля безпеки — цей аварійний сценарій потребує окремого розширення протоколу відновлення.

### 3. FB2/EPUB: спільний парсер у паралельних запитах

**Код:** `Fb2ContentExtractor.java`, `EpubContentExtractor.java`.

Spring-компоненти витягування тексту є спільними між запитами, а `XMLInputFactory` не має універсальної гарантії потокобезпечного використання. Замінено спільний екземпляр фабрики на `ThreadLocal<XMLInputFactory>`, що зберігає переваги повторного використання в межах одного потоку, без одночасного доступу іншого потоку.

**Новий тест:** 80 змішаних паралельних витягувань FB2/EPUB з одним набором компонентів.

## Подальші ризики для окремого детального аудиту

1. **Ранній збій `closeCurrentCollection()` після створення `.restore.pending`:** потребує адресного тесту й явного протоколу відкриття/очищення маркера.
2. **Операції переміщення без атомарного no-replace у всіх файлових системах:** необхідно перевірити поведінку під час конкурентного створення цільового файлу, особливо NTFS та мережевих дисків.
3. **Неперевірений частковий staging-файл при збоях копіювання:** не можна видаляти його без доказу володіння; потрібен захищений тимчасовий файл із окремим ідентифікатором операції.
4. **Велике впорядкування після аналізу:** замір часу `MOVE`, `MOVE_AND_RENAME`, `CONVERT`, `OPTIMIZE` із реальною SQLite-базою, журналом відновлення й перевіркою файлів після аварійного переривання.
5. **Windows UI:** дії всіх кнопок, гарячі клавіші, відкриття/закриття колекцій, переключення обкладинок, робота читача, оновлення застосунку та пристрої.

**Обмеження:** автоматизовані тести не доводять відсутності всіх помилок. Запуск Windows-дистрибутива і випробування користувацької бібліотеки в цій ітерації не виконувалися.

# MyHomeLib 8.0.0 — ітерація 55: стабільне відображення обкладинок
**Дата:** 9 жовтня 2026 року. **Основа:** повний архів ітерації 54.

## Що підтверджено

1. У журналі `myhomelib.log` — **159** запусків `COVER_START` у презентаційному шарі; **82** послідовні запуски були для того самого ідентифікатора книги, **79** із них мали інтервал менш ніж 2 с (медіана — **93 мс**). Це не означає, що всі ці запуски є помилками чи кожен створив візуальне мерехтіння.
2. Контролер `BookDetailsController.loadBookDetails()` ініціює обкладинку негайно з вибраного `BookDto`, а після завершення асинхронного аналізу знову викликає `showCover(session.book())`.
3. Під час нового запиту `CoverPresenter.showCoverInternal()` до виправлення виконував `coverImageView.setImage(null)`, навіть якщо залишалась видимою обкладинка цієї самої книги. Новий результат знову встановлювався в JavaFX-контролі. Це узгоджується зі швидким мерехтінням/підміною.
4. Для книги «Пожиратель душ. Том 18» журнал фіксує завершення першого рендеру о **11:10:34.730** та початок наступного запиту о **11:10:34.775** (інтервал **45 мс**). Обидва результати мали 58 379 байтів; ідентичність байтів у старому журналі не підтверджується.

## Зміни

- Коли уточнюються дані **тієї самої книги в тій самій колекції**, поточна обкладинка залишається на екрані до отримання нового результату.
- SHA-256 від байтів обкладинки обчислюється **в робочому потоці**; для побайтово однакових результатів (за криптографічним відбитком) повторний JavaFX `Image` **не створюється**, а відображувана текстура зберігається.
- Якщо дані обкладинки справді змінилися, відображення коректно оновлюється, без проміжного очищення.
- Під час переходу до іншої книги або іншої колекції попередня обкладинка прибирається негайно, щоб уникнути показу чужого зображення.
- Захист від результатів застарілих запитів збережено. Відкладений `clearCover` не повинен стирати новішу вже завантажену обкладинку.
- Стан відображуваної обкладинки відділено від стану активного запиту, щоб швидкий третій запит тієї самої книги не викликав прихованого очищення.

## Перевірка

- `mvn -o -DskipTests compile`: **21/21 модуль, BUILD SUCCESS**.
- Адресні тести: `CoverPresenterLifecycleContractTest` (1), `CoverPresenterFlickerRegressionTest` (2), `BookWorkspaceControllerAsyncTest` (1): **4/4 без помилок**, `BUILD SUCCESS`, JavaFX запускали під `xvfb-run` на Linux.
- Сценарії: дві послідовні версії DTO тієї самої книги з ідентичними байтами зберігають **ту саму JavaFX Image**; нові байти приводять до оновлення; інша книга негайно очищає попереднє зображення; старий завершений запит не перезаписує нову книгу.

## Межі перевірки

- Візуальне ручне тестування у Windows **не проводилось**. Наведені результати — автоматизовані JavaFX-тести у Linux та компіляція усіх модулів без повного тестового набору.
- Фізичний вміст книг, INPX та користувацькі дані не змінювались.
- Байтова ідентичність обкладинок для старих випадків у журналі невідома. Для нових запитів застосовано SHA-256, який практично виключає хибне визнання різних байтових зображень однаковими.
- Прискорення завантаження файлів не вимірювалося; оптимізовано саме видимість та повторне декодування зображень, але не усунуто другий запит до сервісу обкладинок у всіх випадках.

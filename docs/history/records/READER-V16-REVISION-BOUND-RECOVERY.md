# Reader V16 — recovery-журнали із прив'язкою до ревізії SQLite

## Підтверджений ризик

В історичному форматі `*.pending` (версія 1) зберігалися лише ідентичність
колекції/книги, старий якір, нова позиція та контрольна сума. Після видалення
й повторного створення рядка `reading_progress` старий якір міг повторитися,
хоча покоління та ревізія SQLite були вже іншими. Відновлення за однією
рівністю текстових якорів могло застосувати застарілу позицію.

## Захист

- Формат **2** додає `expectedRevision` до тіла журналу **перед SHA-256**;
  підписана контрольна сума охоплює й ревізію. Для існуючого рядка це
  невід'ємна ревізія; для відсутнього — токен покоління, який повертає
  `ReadingProgressRepository.revisionWhenAbsent()`.
- Reader записує цей токен в обидва журнали **перед SQLite COMMIT**. Під час
  запуску журнал відтворюється лише тоді, коли збігаються і старий якір,
  і спостережена ревізія/покоління. Незбіжність залишає журнал на диску
  для ручної діагностики; SQLite не змінюється.
- Формат **1** залишається читабельним. Якщо SQLite повертає ревізію,
  стара версія журналу не має достатніх доказів для автоматичного відтворення;
  вона також зберігається на диску. Старі тести з неверсіонованими mock
  з'єднаннями продовжують підтримувати legacy-поведінку.
- Якщо SQLite вже містить саму відновлювану позицію, журнал можна безпечно
  підтвердити й очистити без додаткового SQL-запису.
- Формат не потребує нової міграції: спирається на схеми V72/V73.

## Регресії

`ReaderPositionRecoveryJournalTest` та `ReaderAudioRecoveryTest`: різна
ревізія за однакового старого якоря, коректний replay за рівної ревізії,
видалене покоління, legacy-захист і спроба підмінити підписану ревізію.

## Обмеження

Контроль ревізій діє лише для клієнтів, що використовують версіоноване
збереження. Старий код, який виконує сліпий `UPSERT` або обходить SQLite
транзакції/покоління, залишається ризиком. Реальні Windows/NTFS, примусове
вимкнення живлення та міграція оригінальної бази в цьому циклі не тестуються.

# V23: прив'язка Undo до незмінної ідентичності колекції

## Підтверджена регресія на V22

`UndoLibraryOrganizationUseCase.undo(operationId, expectedCollectionId)` порівнював лише переданий користувацьким інтерфейсом `expectedCollectionId` з поточною колекцією. При виклику `undo(operationId)` перевірка повністю пропускалася. **Ідентифікатор колекції з незмінного запису журналу не перевірявся.** Тому користувацька/помилкова передача ID активної колекції могла ініціювати відкат операції іншої колекції.

Негативні JUnit-тести на V22: `journalCollectionMustMatchEvenWhenCallerPassesActiveCollectionId`, `omittedCallerCollectionMustNotBypassDurableJournalCollection` — **FAIL** (відкат дозволено). Цільові тести виправленої V23 — PASS.

## Правило V23

* `OrganizationJournalPort.findOperation(UUID)` повертає незмінний запис **саме вказаної операції**, у тому числі для `COMPLETED` / інших термінальних станів. SQLite-реалізація використовує параметризований запит за первинним ключем. За замовчуванням кастомні адаптери повертають `Optional.empty()` (fail closed).
* Перед першим читанням/зміною файлів потрібен запис журналу; якщо його немає — відкат заборонено.
* Якщо в журналі збережено непорожній `collectionId`, він **обов'язково** збігається з поточною колекцією. Якщо викликач передає непорожній ID, він також **обов'язково** збігається з журналом. Відсутній `CollectionLifecyclePort` не дозволяє пропустити цю перевірку.
* Старі записи без `collectionId` при наявному `CollectionLifecyclePort` не відкочуються автоматично. Потрібен ручний аналіз їхнього походження, інакше неможливо довести межу ізоляції колекцій.
* Старий варіант конструктора без `CollectionLifecyclePort` підтримується тільки для ізольованих кастомних/тестових журналів без ID колекції; для записів із ID відкат закрито.

## Межі доказів

Перевірено негативні та позитивні сценарії на тимчасових файлах, загальну Maven-збірку, читання SQLite-запису `COMPLETED`. Це **не** доводить атомарність одночасної зміни активної колекції безпосередньо після перевірки ідентичності. Не перевірено Windows/NTFS, жорсткий kill під час відкату, наявність реальної `Flib.db`, роботу на відновлених робочих даних. Повторна спроба після частково завершеної операції й безпечність усіх гілок файлообігу потребують окремих сценаріїв fault injection. Реліз не production-ready.

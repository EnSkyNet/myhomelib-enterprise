# MyHomeLib Enterprise 8.0.0 R18 — V18: перевірки узгодженості

**Основа:** V17 із SHA-256 `5253c65e319b8457a2736e5d77f70a96d91285753043a60a040113df260346f8`.
**Статус:** Linux release candidate; Windows production sign-off **відсутній**.

## R18-SNAPSHOT-01 — джерельний SQLite snapshot

У V17 адаптер `SqliteBookUserStateTransferAdapter` читає `reading_progress`, `reading_history`, `reading_stats`, `bookmarks` і профілі окремими SELECT на автоматичній фіксації. Навіть за цілком транзакційного запису до цілі джерельний стан може бути складений із різних SQLite commit. Тест із тригером на цільовій базі примусово змінює джерело під час перенесення й на V17 одержує старий `reading_progress` та новий `reading_history`.

У V18 після відкриття й обмеження source-з'єднання `PRAGMA query_only=ON` виконується `setAutoCommit(false)` перед першим SELECT. Перший фактичний SELECT фіксує джерельний SQLite snapshot; всі наступні таблиці та чанки до 400 `book_id` читають той самий стан. WAL дозволяє конкурентним writer-процесам комітити новий стан, не змінюючи зафіксованого знімка. Об'єкт Connection закривається лише після перенесення. Цільова транзакція зберігає V17 rollback.

**Межі:** це не атомарна транзакція двох SQLite-файлів. Новий запис у джерелі після початку SELECT не потрапить до перенесеної цілі; зовнішнє узгодження, retry/conflict-протокол або гарантована зупинка writer потрібні, перш ніж прибирати вихідну книгу. `SQLITE_BUSY`, WAL checkpoint і kill-point на NTFS потребують окремого тесту.

## R18-MERGE-01 — прогрес полиці після об’єднання книг

У V17 `mergeBookUserScalars` обирає `books.progress` як максимум від двох книг; `mergeReadingProgress` пізніше обирає **найсвіжіший** рядок `reading_progress` за `updated_at`. Якщо остання позиція становить 35%, а старіший екземпляр колись мав 70%, каталог повідомляє 70%, а Reader — 35%. Відтворення на V17: `expected 35 but was 70`.

У V18 після вибору актуального рядка та підвищення ревізії `reading_progress` каталогові записується відсоток з цього рядка в **тій самій транзакції merge**; його обрізано до [0, 100] та округлено як для звичайних полиць. Якщо `reading_progress` узагалі немає, попередня політика об’єднання максимуму скалярних станів залишається.

## Нові інтеграційні тести

* `SqliteBookUserStateTransferSnapshotTest`: міжтаблична зміна на двох файлах SQLite/незалежних з’єднаннях, а також зміна між чанками з 401 `book_id`.
* `SqliteBookMergeAdapterIntegrationTest.mergeKeepsShelfProjectionAlignedWithChosenMostRecentReadingPosition`: реальна Flyway-схема + merge двох книг і перевірка збереження вибраної останньої позиції у каталозі.

## Незакриті приймальні критерії

1. Контроль read/write-конфлікту з живими сторонніми Reader-клієнтами й синхронізацією через пристрої, включно з `revision == null` legacy-upsert.
2. Windows/NTFS/UNC/DPAPI/антивірус, реальна JavaFX-сесія, папки на різних томах, блокування першої книги в організаторі.
3. `SQLITE_BUSY`, WAL checkpoint, обрив живлення під час переходів «файл → журнал → SQLite», реальна копія `Flib.db`.
4. Повномасштабний імпорт 707154 записів INPX у нову SQLite-колекцію та багатогодинна сесія Lucene/JavaFX. Прочитати INPX у probe-тесті — не те саме, що виконати цей імпорт.
5. Інвентаризація всіх legacy-операцій прямого UPDATE reader стану; потрібна політика усунення обходів CAS.

Для Windows smoke використовувати **окремі копії** книги й БД. Перевірити NTFS ACL, довгі та UNC-шляхи, доступ із двох процесів, антивірусне блокування, DPAPI restore, відновлення після аварійного вимкнення, перегляд/застосування/скасування організації на тестовій копії, збереження текстових/аудіоякорів і журналів. Заборонено запускати масові файлові операції на робочій бібліотеці без дозволу.

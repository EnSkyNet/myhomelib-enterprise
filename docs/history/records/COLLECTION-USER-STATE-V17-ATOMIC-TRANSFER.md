# V17 — атомарне перенесення стану читання між колекціями

## Підтверджені проблеми V16

1. `SqliteBookUserStateTransferAdapter.copyReadingProgress()` переносив `reading_progress.percent`, але не оновлював відповідне `books.progress` у цільовому каталозі. Полиці, фільтри й відсоток читання могли показувати застаріле значення.
2. `transferCopiedBookState()` без зовнішньої транзакції виконував послідовні SQL-операції з автокомітом. Якщо закладка конфліктувала після успішного перенесення прогресу, перший запис залишався в SQLite. При виклику з транзакційного хука BookSaver частину ризику перекривала зовнішня транзакція, але сам порт не гарантував атомарність.
3. У старих БД можуть бути відсутні або вимкнені зовнішні ключі, тому перенесення `reading_progress` без відповідного `books` могло створити осиротілий стан.

## Виправлення

- Виконувати **весь** перенос стану всіх переданих книг через `CollectionTransactionExecutor`, який приєднується до поточної Spring-транзакції, якщо вона є, або створює нову.
- Після перенесення прогресу узгоджувати цільове `books.progress` з `reading_progress.percent` у тій же транзакції. Значення відсотка обмежене діапазоном 0–100, округлене так само, як у репозиторії звичайного прогресу.
- Перед оновленням проєкції відхиляти прогрес для відсутніх у цільовій БД книг, з повним відкатом SQL-операцій.
- Зберігати існуючий перенос окремих текстових/аудіоякорів та збільшення ревізії при конфлікті; **жодної нової міграції SQLite**.

## Докази

Негативний прогін нових JUnit-тестів на незміненій V16: **2 failures** — невідповідність `books.progress` і частковий перенос після пізнього конфлікту закладки. Після виправлення чотири інтеграційні тести PASS: два початкові негативні сценарії, заборона сирітського прогресу і відкат через межу двох пачок по 400 ID.

Тести працюють із двома тимчасовими SQLite-файлами, а не з користувацькою бібліотекою. Повний production-допуск вимагає окремого Windows/NTFS приймання на копії реальних даних.

## Залишкові ризики

- Старі або сторонні SQLite-записувачі можуть обходити контроль ревізій.
- У транзакції перенесення підключення до бази **джерела** відкрите для читання; багатоколекційна транзакція між двома SQLite-файлами не є глобально атомарною. Джерело в цій операції не змінюється.
- Знімок джерела, конкурентне редагування вихідної бібліотеки й міжпроцесні блокування потребують окремого стрес-приймання на Windows.
- Ніяких масових операцій над робочою бібліотекою не виконували.

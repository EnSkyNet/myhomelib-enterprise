# MyHomeLib R18 — виправлення вилучення тексту та оптимізація пам’яті

Дата: **2026-10-11**. Основа: наданий MyHomeLib Enterprise 8.0.0 R18 з попереднім аудитом повнотекстового пошуку від 2026-10-10. Цей пакет містить наступний етап виправлень: FB2/EPUB/TXT extraction, коректні текстові зміщення та обмеження витрат оперативної пам’яті.

## Що виправлено

| Ділянка | Зміна та результат |
| --- | --- |
| `ExtractedContent` | Прибрано повторне збирання всієї книги лише для перевірки узгодженості. Наявний текст перевіряється через `regionMatches`, межі розділів і символи-роздільники. |
| `ContentDocumentBuilder` | Прибрано загальний mutable-буфер книги та проміжні списки абзаців. Завершені розділи зберігаються одразу; для одного розділу його рядок повторно використовується як повний текст. |
| `NormalizedTextBuffer` | Нормалізація відбувається під час читання фрагментів. Послідовності пробілів не накопичуються, бюджет перевіряється перед додаванням символу. |
| FB2 | Абзаци одразу передаються builder; StAX передає масив символів без зайвого проміжного `getText()`-рядка. Збережено обробку inline-елементів, CDATA та кількох body. |
| EPUB | Вкладені блоки та `<br/>` більше не склеюють сусідні слова. Звичайне inline-форматування не додає зайвих пробілів. Ліміт тексту спільний для всього spine. |
| TXT | Необмежений `readLine()` замінено читанням блоками по 8192 символи. Скасування працює й усередині довжелезного рядка; оброблено LF, CR та CRLF, зокрема на межі буфера. |
| UTF-8 | Проба 16 KiB, обрізана всередині багатобайтового символу, більше не помилково визначається як legacy-кодування. Для повного файла збережено строгу перевірку. |
| Повнотекстовий індекс | Версію схеми підвищено з 1 до 2, щоб старі зміщення не застосовувалися до тексту з виправленою нормалізацією. |

Збережено ліміт **67 108 864 UTF-16 code units** нормалізованого тексту, включно з роздільниками. Це 64 × 1024 × 1024 одиниці UTF-16, а не 64 MiB вхідного файла чи гарантія такого самого розміру heap. Додано окремий ліміт **250 000 непорожніх абзаців** на артефакт, оскільки короткі абзаци також створюють об’єкти anchors. Перевищення ліміту повертає `FAILED` без часткового `ExtractedContent`.

Ці обмеження стосуються extraction-адаптерів, які використовує індексація та інші споживачі вилученого тексту, зокрема Web Reader. Підсумкові текст і розділи лишаються в пам’яті: алгоритм не має константного споживання RAM. Версії залежностей та production-параметри heap цим патчем не змінювалися.

## Обов’язкова дія після оновлення

У вікні перевірки цілісності колекції виконайте **одноразову перебудову індексу вмісту / повнотекстового індексу**, якщо він створений попередньою версією. Schema 1 тепер позначається як несумісна. Пошук і часткове оновлення старого індексу блокуються до його перебудови.

Схема SQLite й індекс метаданих каталогу цим патчем не змінюються. Оригінали книг зберігаються без змін.

## Перевірки, виконані під час цієї задачі

У пов’язаних наборах пройдено **37 тестів без failures/errors/skips**. Із них **16 тестів додано в цьому етапі**; решта перевіряють раніше наявні контракти.

| Набір | Усього тестів | Додано |
| --- | ---: | ---: |
| `ExtractedContentTest` | 4 | 4 |
| `ContentDocumentBuilderTest` | 3 | 3 |
| `ContentExtractionResourceRegressionTest` | 5 | 5 |
| `ContentExtractorContractTest` | 11 | 2 |
| `TextStreamDecoderTest` | 2 | 1 |
| `LuceneContentIndexServiceIntegrationTest` | 12 | 1 |
| **Разом** | **4 + 3 + 5 + 11 + 2 + 12 = 37** | **4 + 3 + 5 + 2 + 1 + 1 = 16** |

Перевірено Unicode і порожні розділи, неправильні зміщення, сумарні бюджети тексту та anchors, ранню відмову до EOF, скасування довгого TXT-рядка, межі CRLF, FB2 inline/CDATA, EPUB-блоки й spine, усі точки розриву 2-, 3- та 4-байтових UTF-8-символів, несумісність старого індексу та відновлення після перебудови. Під час попереднього етапу регресії UTF-8 і склеювання EPUB-тексту відтворювали помилки на початковому коді.

Це результати запусків у межах цієї задачі на коді збереженого пакета; сирі Surefire XML і журнали тих запусків до фінального архіву не включено. Після відновлення пакета production- і test-код не змінювався, оновлено документацію. Архітектурну перевірку повторно виконано перед пакуванням; її журнал додано поруч зі звітом.

**Повний root `clean verify` не підтверджено.** У середовищі виконання виявлено такі перешкоди:

- `ProcessExecutionSupportTest#timeoutTerminatesDescendantProcessTree` падав і на початковому, і на зміненому коді: `ProcessHandle.descendants()` не показував створений дочірній процес. Для ширшого прогону командою виключався лише цей метод; у вихідному коді він лишається активним.
- Графічні тести спочатку блокувала відсутня native-залежність `libXtst.so.6`; після її підготовки Reader пройшов далі. Наступний прогін UI виявив відсутність `libawt_xawt.so` у headless JRE. Завершеного повторного root-прогону з повним desktop JRE немає.
- Проміжний запуск із `JAVA_TOOL_OPTIONS` забруднював stderr дочірньої Java-програми службовим повідомленням. Наступний запуск передавав heap-параметри без цієї змінної. Це не виправлялося зміною тестових очікувань або production-коду.

Тому пакет не позначається як повністю перевірений для Windows чи як `21/21 BUILD SUCCESS`. Потрібен фінальний root-прогін у повному desktop-середовищі без виключення тесту дерева процесів. Старі повні результати з інших дат у документації є історичними й не підтверджують цей патч.

## Відтворення цільових тестів

Потрібні JDK 21, Maven 3.9.16 і залежності з POM. Для offline-режиму вкажіть фактичний каталог підготовленого репозиторію замість `/path/to/repository`:

```bash
mvn -o -B -ntp -Pproduction \
  -Dmaven.repo.local=/path/to/repository \
  -pl myhomelib-infrastructure -am \
  -Dtest=TextStreamDecoderTest,ExtractedContentTest,ContentDocumentBuilderTest,ContentExtractionResourceRegressionTest,ContentExtractorContractTest,LuceneContentIndexServiceIntegrationTest \
  -Dsurefire.failIfNoSpecifiedTests=false test

python3 tools/architecture-check.py
```

Загальна перевірка в повному desktop-середовищі: `mvn -Pproduction clean verify`. Linux UI-тестам потрібні X/GTK, повний desktop JRE та доступний дисплей або Xvfb.

## Перевірка пам’яті та межі висновків

Додано `ContentExtractionMemoryProbe.java` і `tools/content-extraction-memory-probe.py`. Runner запускає кожен FB2/TXT в окремій JVM, збирає Linux peak RSS через `wait4`, сумарні виділення пам’яті потоку extraction і час обробки. SHA-256 охоплює текст, metadata розділів та всі anchors; при розбіжності між запусками runner завершується помилкою. Текст книг не записується у CSV.

Під час попереднього етапу виконувалися A/B-вимірювання трьох наданих великих FB2 і синтетичного TXT; digest тексту та зміщень збігався. Сирий CSV того етапу не входить у цей пакет, а точна початкова версія для повторного A/B недоступна. **Новий відсоток скорочення RAM у фінальному звіті не заявляється.** Усунення зайвих повних копій підтверджується зміною алгоритму; ефект на конкретному комп’ютері слід виміряти доданим probe.

```bash
python3 tools/content-extraction-memory-probe.py \
  --java "$JAVA_HOME/bin/java" \
  --classpath-file probe-classpath.txt \
  --output memory-current.csv --runs 3 --heap 512m \
  /path/to/book.fb2 /path/to/book.txt
```

`probe-classpath.txt` має містити одним рядком `myhomelib-benchmark/target/classes`, production classes потрібних модулів і runtime jars, розділені `:` у Linux. Спочатку скомпілюйте benchmark-модуль разом із залежностями. Для справжнього A/B додайте `--baseline-classpath-file` з точними попередніми production classes і тим самим probe; не реконструюйте стару реалізацію за описом.

Allocations — обсяг усіх виділень за операцію, не одночасно зайнятий heap. RSS — пік усього процесу, включно зі стартом JVM і контрольним хешуванням. Ці метрики не є idle RAM повного Windows desktop-застосунку; час і RSS залежать від середовища. Реальні EPUB, повторний імпорт великого INPX, Windows-пакування та тривалий soak у цьому етапі не підтверджено.

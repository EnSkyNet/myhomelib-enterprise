# MyHomeLib Enterprise 7.1.0 RC3 — hardening checkpoint 04, 2026-09-04

This checkpoint focuses on migration **semantic data preservation**, not merely on whether Flyway can reach V48.
The historical SQL files remain immutable so existing Flyway checksum history is not broken.

## Deep migration findings

Two historical migration paths could lose valid user/catalog data when upgrading an old database:

1. **V7 author-name collapse**
   - V7 deletes duplicate author rows grouped only by `(first_name,last_name)` and then creates a unique index.
   - V34 later removes that uniqueness because author names are lookup attributes, not person identities.
   - Therefore an upgrade starting before V7 could permanently lose authors that share first/last name but differ by
     middle name or represent separate external identities; their `book_authors` links could also be lost.

2. **V25 → V26 Reader progress recreation**
   - V25 adds `chapter_title`, `chapter_id`, and `reading_time_seconds` to `reading_progress`.
   - V26 recreates the table but copies only the older columns.
   - A database that was actively used while exactly on V25 could therefore lose those Reader fields during upgrade.

## Implemented compatibility guard

Added `LegacyMigrationDataGuard`, called by `DatabaseMigrationAdapter` around Flyway migration.

- Before a pre-V7 migration, only at-risk duplicate-name author rows and their book-author relations are copied into
  durable guard tables.
- Before a V25 → later migration, Reader progress fields are copied into a durable guard table.
- Flyway then runs the original, unchanged migration files.
- After the final schema is available, guarded rows are restored and verified before the guard tables are dropped.
- Guard tables intentionally survive process termination. If the process stops after the destructive historical
  migration but before restoration, the next migration attempt resumes recovery from the existing guard tables.
- V1–V36 migration bytes were not modified; the retained SHA-256 migration manifest still validates.

This protects **future upgrades that have not yet crossed the affected historical migration**. Data already lost by a
previously completed V7/V26 upgrade cannot be reconstructed without an external backup/source because the discarded
values are no longer present in the database.

## Release-gate tooling repaired

The older `tools/build-check-v7.py` itself had stale release assumptions:

- expected only V1..V44 although the current schema is V48;
- checked the v7 → v7.1 upgrade only through V44;
- had an undefined `errors` variable in the root-documentation invariant;
- did not assert the new migration-guard integration.

The checker now validates V1..V48, immutable V1..V36 checksums, the V37..V48 upgrade range, current root docs, and the
migration-guard source invariants.

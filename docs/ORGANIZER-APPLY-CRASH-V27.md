# Організатор V27: наскрізні контрольовані обриви Apply та перевірка прямого Undo

## Вихідна точка

Цей цикл базується **лише на консолідованій вихідній V26**. Схема БД і SQL-міграції не змінені. Випробування проводяться винятково з тимчасовими SQLite-файлами та тестовими книжками. Робоча `Flib.db` не відкривається.

## Виправлення: прямий Undo не має обходити strict recovery manifest

`GetLibraryOrganizationStatusUseCase` у V26 перевіряє `LibraryOperationCrashManifestReader.read()` і відхиляє розірваний журнал. Але публічний `UndoLibraryOrganizationUseCase.undo()` цю перевірку оминав та міг відновлювати файли попри пошкоджений журнал. Це не доведена втрата даних, але підтверджений обхід консервативної перевірки recovery.

У V27 перед читанням елементів для відкату перевіряються наявний crash-manifest (строгий reader), UUID операції й кореневі шляхи джерела/призначення в порівнянні з авторитетним записом SQLite. Неповний, пошкоджений або чужий manifest блокує Undo з вимогою ручної перевірки **до першої файлової операції**. Для історичних записів, які не мають manifest, збережена попередня поведінка; вона потребує окремого аудитування перед production-використанням.

Тест `directUndoMustRejectCorruptCrashManifestBeforeChangingFiles` на V26 з доданою регресією: FAIL (відкат був дозволений); на V27: PASS, target не змінюється.

## Справжні JVM kill-point сценарії, застосовані до виробничого Apply

`SqliteOrganizerApplyCrashIntegrationV27Test` створює тимчасову SQLite-базу в режимі WAL, фізичні source/target, запускає окрему JVM із **реальним** `ApplyLibraryOrganizationUseCase` й `SqliteOrganizationJournalAdapter`. На рівні адаптера тестова обгортка завершує процес через `Runtime.halt(83)` на трьох межах:

| Точка обриву | Очікуваний стан SQLite після нового підключення | Файли після обриву | Recovery |
|---|---|---|---|
| перед переходом до `VALIDATED` | `STAGING` | джерело існує, ціль відсутня | rollback без зміни книги |
| перед переходом до `COMMITTED` | `VALIDATED` | джерело прибране, ціль має той самий SHA-256 | Undo відновлює джерело |
| одразу після запису `COMMITTED`, до manifest event | `COMMITTED` | джерело прибране, ціль має той самий SHA-256 | Undo відновлює джерело |

Кожна перевірка виконує нове відкриття SQLite, `PRAGMA integrity_check`, строгий парсинг manifest, класифікацію `ROLLBACK_AVAILABLE`, справжній `UndoLibraryOrganizationUseCase`, контроль SHA-256 та стан `ROLLED_BACK`. Ключова межа тесту: обрив виконується на тестовій обгортці **порту журналу**, але всередині справжнього виклику Apply, а не за окремим ручним сценарієм файлових операцій.

## Що не підтверджено

- Відсутність зависання першої книги на Windows/NTFS/SMB/UNC, поведінка антивіруса та DPAPI.
- Структура транзакцій і гарантії `fsync` за **реальної фізичної** втрати живлення та Windows I/O.
- Відновлення всіх дій конвертації / оптимізації / архівів, усіх точок між публікацією й каталогом, конкурентні зовнішні записи.
- Політика безпечного автоматичного recovery: тести підтверджують явний Undo після перевірок; вони не є дозволом на автоматичне видалення чи заміну файлів.

**Релізний стан залишається Linux release candidate, не Windows production-ready.**

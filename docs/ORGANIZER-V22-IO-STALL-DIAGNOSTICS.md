# V22 — діагностика блокувань файлового конвеєра організатора

Основа — консолідована V21. Міграції SQLite й формат recovery не змінено.

## Зміна

- Один демон-потік на **активну операцію Apply**, який лише спостерігає за `Thread.getStackTrace()` робочого потоку. За відсутності нового етапу або збільшення кількості байтів протягом 30 секунд записує `ORGANIZER_IO_STALL` на рівні WARN. Повторює не частіше одного разу на 30 секунд до поновлення прогресу, не перериває `read`/`write`, не перезаписує, не очищає файлів, не змінює SQLite.
- Фіксуються `operationId`, `itemId`, `stage`, `bytes`, `silentMs`, `threadState`, 14 верхніх кадрів JVM. Заради приватності не записуються повні імена книг чи шляхи в окремі поля монітора. **Стек сам по собі може розкривати контекст**; перед передачею перевірте журнали.
- Фіксуються початок і прогрес preflight SHA-256 на звичайних файлах, навіть якщо вся перевірка першої книги триває довго. Для записів усередині ZIP збережено попередній механізм хешування, який має лише `PREFLIGHT_ARCHIVE_HASH_START`/`DONE` без поточного лічильника байтів. Для звичайної SHA-256 перевірки нове `ORGANIZER_PREFLIGHT_HASH` (INFO) друкується на першому блоці та не частіше ніж кожні 5 секунд.
- Для переміщення/перейменування додано внутрішні позначки copy, publish, catalog і source-remove; уже наявні `ORGANIZER_COPY`/`ORGANIZER_STAGE` збережені.
- Завершення `Apply` закриває монітор. Діагностичні помилки не повинні змінювати результат користувацької операції.

## Відтворення й обмеження

JUnit `OrganizerIoStallMonitorTest`: штучний CountDownLatch-блокований робочий потік, гарантована діагностика, незмінність файла, припинення повідомлень після close, відсутність хибних попереджень при збільшенні байтів і контроль streaming SHA-256.

Для справжнього Windows/NTFS зависання потрібна **окрема тестова копія бібліотеки**; Linux-імітація `CountDownLatch` не відтворює зависання драйвера, антивіруса, SMB, Windows Filter Manager, файлової системи та поведінку DPAPI. Встановлення тайм-ауту для `Files.newInputStream().read()` у цьому циклі **не виконувалось**, адже Java cancellation/interrupt не гарантує безпечного розблокування нативного I/O.

Інструмент `tools/collect-organizer-stall-windows.ps1` робить три незалежні `jcmd Thread.print -l` зрізи й записує їх лише в обраний каталог. Приклад (PowerShell із JDK 21 в PATH):

```powershell
.\tools\collect-organizer-stall-windows.ps1 -ProcessId 12345 -OutputDirectory 'C:\Temp\mhl-diag'
```

**Неперевірено:** робота цього PowerShell-сценарію в Windows, доступність JVM Attach API у запакованому desktop runtime, NTFS/UNC, реальні колізії, жорстка втрата живлення, відновлення реальної БД, робота з реальним першим FB2 і багатогодинний JFR/heap.

## Незалежний чистий прогін: зафіксована тестова гонка

Перша спроба повного `clean verify` з V22 ZIP виявила успадкований від V21 хибний
тест `GoogleBooksMetadataProviderTest.requestDeadlineMapsToTimeout`: він вимагав
`received.getCount()==0` уже після коректного `TIMEOUT`, хоча за навантаження
100-мс дедлайн може завершитися **раніше**, ніж loopback HTTP-сервер прийме
запит. Це не доказ помилки HTTP-провайдера. Прибрано припущення про гарантовану
доставку, збережено перевірку типу помилки `TIMEOUT` і затримку відповіді 500 мс.
Журнал першого невдалого прогону слід зберігати разом із повторним успішним.

# MyHomeLib Enterprise 8.0.0 R18 — додатковий цикл аудиту V4

База змін: консолідований вихідний ZIP V3 від 16.10.2026 (SHA-256 у зовнішньому звіті).
Цикл V4 **не є** сертифікацією production-ready: повна Maven/JUnit-збірка і Windows-приймання не виконані.

## Підтверджені дефекти, виправлення та регресії

**R18-25 / P0 — SQLite: залишкова проєкція після синхронізованого видалення.**
`SqliteReadingProgressRepository.deleteByBookId()` видаляв тільки `reading_progress`,
не очищуючи `books.progress`. Після sync tombstone полиця могла показувати
застарілий відсоток прочитання. Тепер обидві операції входять до однієї
транзакції з `busyRetry`, `collectionTransactionTemplate` або безпечною
транзакційною альтернативою. Тести: два JUnit-тести на успішне видалення та
відкат після `RAISE(ABORT)`, три Python-тести SQL-контракту.

**R18-26 / P0 — Reader: знищення пошкоджених доказів аварійного відновлення.**
Методи `prepare()` текстового й аудіожурналів без перевірки замінювали
існуючий `.pending` навіть після пошкодження. Це приховувало наслідки
аварії або несправного запису. Тепер наявний файл перевіряється через
`load()`: пошкоджений файл зберігається незмінним, збереження завершується
відмовою; підтверджений коректний журнал можна оновити новішим станом.
Доказ: Java regression harness на V3 відтворив помилку
`AssertionError: corrupt text was overwritten`, на V4 — 256/256 PASS.
Додано чотири JUnit-сценарії для обох типів книг.

Обмеження: перевірка існування/читання/заміни файлу не є міжпроцесною
транзакцією. Взаємодію **двох незалежних процесів** і відмову живлення
потрібно окремо перевіряти на Windows/NTFS. `books.progress` залишається
спільним підсумковим полем, а text/audio мають спільний `anchor_id`;
проектування незалежних сховищ для двох режимів у цьому циклі не виконано.

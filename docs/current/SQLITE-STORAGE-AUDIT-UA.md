# Перевірка шляхів бібліотеки MyHomeLib перед перейменуванням папок

**Діє для вихідної версії R18 (етап 3, 15.10.2026).**

## Навіщо потрібна перевірка

Багато книг уже переміщені до папок з іменами авторів. Перед будь-яким новим перейменуванням необхідно переконатися, що шлях, записаний у `books.collection_root`, `books.folder`, `books.file_name`, відповідає файлу на диску. Один архів ZIP може містити кілька логічних книг, які посилаються на **один** фізичний файл. Переміщення з оновленням лише одного запису залишить інші книги з недійсними шляхами.

`tools/audit-catalog-paths.py` працює **тільки на читання**: не змінює SQLite і не переміщує файлів.

1. Закрийте MyHomeLib. Створіть **узгоджену резервну копію** бази через SQLite Backup API або штатну функцію резервного копіювання. Не копіюйте лише `.db`, поки програма працює з `.db-wal`.
2. Знайдіть фактичну кореневу папку колекції, яку застосунок використовує для шляхів книг. **Папка, що містить файл `Flib.db`, не обов’язково є коренем книг.**
3. Запустіть з Python 3:

   ```powershell
   py -3 tools\audit-catalog-paths.py --catalog "C:\Backup\Flib.db" --root "D:\Flib" --output "C:\Backup\catalog-path-review.csv"
   ```

   Значення `D:\Flib` — **лише приклад**. Замініть фактичним коренем із налаштувань колекції.
4. Перегляньте CSV, особливо `ФАЙЛ_НЕ_ЗНАЙДЕНО`, `ІНШИЙ_КОРІНЬ_КОЛЕКЦІЇ`, `НЕБЕЗПЕЧНИЙ_ШЛЯХ` і коментарі про спільні архіви. Якщо частина книг лежить у `D:\Другие`, але у SQLite вказано інший корінь, **не підставляйте** `D:\Другие` навмання та не редагуйте записи вручну.
5. Для першої швидкої перевірки можна використати `--limit 1000`. Якщо `--limit` використано, звіт охоплює лише перші N рядків. За замовчуванням перевіряються всі активні локальні записи. `--include-ok` додає успішні записи до CSV.

## Значення станів

- `ФАЙЛ_ІСНУЄ` — фізичний файл існує за вказаними координатами; це **не** перевірка SHA-256 або змісту EPUB.
- `ФАЙЛ_НЕ_ЗНАЙДЕНО` — фізичного файла за шляхом із каталогу немає.
- `ІНШИЙ_КОРІНЬ_КОЛЕКЦІЇ` — запис спрямовано до іншого кореня; інструмент навмисно не вгадує, де він розташований.
- `КОРІНЬ_НЕ_ВКАЗАНО` — історичний запис без `collection_root`, потрібна ручна перевірка.
- `НЕБЕЗПЕЧНИЙ_ШЛЯХ` — підозрілий або некоректний компонент шляху.
- `ПОСИЛАННЯ_ЗАМІСТЬ_ФАЙЛУ` — символічне посилання або аналог, автоматично змінювати його не можна.
- `СПІЛЬНИХ_ПОСИЛАНЬ` — лічильник логічних книг із повторними координатами фізичного файла, **не сам по собі дефект** (типово для архівів).

## Додатковий захист

При застосуванні плану організатор перевіряє, чи може оновити шлях у керованій SQLite-колекції. Якщо цільовий шлях виходить за її корінь або кілька логічних книг посилаються на один фізичний файл, програма відхиляє такий небезпечний план до зміни файлів. Це **тимчасове захисне обмеження**, а не повна підтримка багатотомного переміщення.

## Що цей етап не виконує

- Не виправляє попередні записи, якщо файли вже були переміщені зі старими шляхами.
- Не перейменовує папки «Ім’я Прізвище».
- Не перевіряє усі посилання на файли в зовнішніх застосунках і кешах.
- Не замінює приймального тестування на Windows із резервною копією реальної бібліотеки.

Після оцінювання результату аудиту можна розробляти **окремий відновлюваний механізм** із перевіркою SHA-256, оновленням усіх залежних записів SQLite, попереднім переглядом і контрольованим відкатом.

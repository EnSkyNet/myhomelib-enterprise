# MyHomeLib R18 — аудит продуктивності повнотекстового індексу

**Подальше оновлення 2026-10-11:** цей документ описує попередній патч пошуку. Наступний аудит extraction підвищує схему повнотекстового індексу до **2** і потребує одноразової перебудови. Твердження нижче про незмінну схему стосується лише попереднього патча. Деталі: `docs/release/CONTENT-EXTRACTION-MEMORY-AUDIT-2026-10-11-UA.md`.

**Дата:** 2026-10-10  
**Область:** `LuceneContentIndexService`, пошук вмісту книг, діагностика стану індексу  
**Статус:** оптимізацію реалізовано; цільові тести пройшли. Повний `mvn clean verify` у цьому циклі не завершився через тайм-аут середовища під час тестів application-модуля. Окремий `mvn -DskipTests package` також завершився тайм-аутом під час компіляції UI-модуля без повідомлення про помилку компілятора. Повний регресійний прогін не позначено як успішний.

## Знайдені проблеми та зміни

1. **Повторне відкриття Lucene reader у кожному пошуку.** Раніше перевірка сумісності відкривала й закривала `DirectoryReader`, після чого пошук відкривав другий reader. Тепер версія схеми перевіряється на reader, який уже використовується для пошуку.
2. **Зайвий точний підрахунок результатів.** Раніше `searcher.count()` виконувався до `searcher.search()` для кожного запиту. Тепер спочатку отримуються `TopDocs`; точний `count()` запускається лише тоді, коли Lucene повертає `TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO`. Точна загальна кількість зберігається.
3. **Повторне створення regex для кожного результату.** Токени запиту й regex для пошуку позиції фрагмента тепер обчислюються один раз на запит; regex нормалізації пробілів повторно використовується.
4. **Непотрібне завантаження stored fields.** Під час формування кожного результату завантажуються лише поля, потрібні для `ContentIndexHit`; збережені anchor-поля не читаються для кожного результату.
5. **Обчислення розміру каталогу.** `Files.walk()` замінено на неповторюваний рекурсивний обхід: Lucene зберігає файли індексу в корені каталогу, тому `Files.list()` рахує звичайні файли верхнього рівня без рекурсивного обходу.
6. **Переповнення offset + limit.** Сума обчислюється в `long`, перш ніж застосувати верхню межу `10 000` до числа результатів, які треба отримати.
7. **Відтворюваність вимірювань.** Опційний benchmark має три прогрівальні ітерації та окремо записує min/median/max для пошуку й `health()`.

## Контрольні тести

`LuceneContentIndexServiceIntegrationTest`: **11 тестів пройшли**, включно з новими перевірками точного підрахунку понад поріг Lucene та великого offset.  
`ContentIndexPerformanceBenchmarkTest`: опційний тест пройшов на 50 000 синтетичних документів, 3 warm-up і 31 вимірювання; всі 50 000 збігів знайдено, індекс каталогу лишився незмінним.

## A/B-вимірювання

Той самий тимчасовий Java probe запускався проти попереднього й оновленого `LuceneContentIndexService`. Кожен варіант створював 50 000 детермінованих розділів із коротким текстом, прогрівав пошук і `health()` трьома ітераціями, а потім виконував 31 вимірювання. Пошуковий запит `commonterm` збігався з усіма 50 000 документами; поверталася перша сторінка до 100 результатів. Середовище — Java 21, Linux, локальна файлова система, один процес на варіант.

| Метрика | До | Після |
|---|---:|---:|
| Пошук, медіана | 9 494 мкс | 6 710 мкс |
| `health()`, медіана | 3 020 мкс | 2 845 мкс |
| Знайдено збігів | 50 000 | 50 000 |
| Розмір індексу | 2 886 614 байтів | 2 886 614 байтів |

Медіанний час пошуку зменшився приблизно на **29,3%** у цьому сценарії. Це результат одного A/B-прогону на синтетичному корпусі, а не latency SLA. Значення часу перебудови не використовуються для заяв про прискорення: перебудова не була ціллю цих змін, а вимірювання можуть залежати від файлового кешу й навантаження хоста.

Окремий benchmark із вбудованого тестового набору збережено в `docs/release/PERFORMANCE-CONTENT-INDEX-50K-2026-10-10.csv`; CSV містить точний результат того запуску.

## Залишкові ризики

- Повний `mvn clean verify` повторно не підтверджений у цьому циклі: одна спроба зупинилася під час тестів application-модуля, а окрема збірка з пропущеними тестами — під час компіляції UI-модуля. У журналі немає діагностичного повідомлення компілятора, яке дозволило б пов’язати тайм-аут із цією зміною.
- Потрібні повторні вимірювання на реальних великих колекціях, різних дисках і Windows.
- Точний `count()` усе ще виконується для широких запитів, коли Lucene повертає нижню межу total hits. Це зберігає контракт точного `total`, але лишається витратною операцією для дуже поширених термінів.
- Формат Lucene не змінювався; версію схеми не підвищено, перебудова індексу для цього патча не потрібна.

# Безпечне виправлення папок авторів (етап 4)

Інструмент `tools/repair-author-folder.py` обробляє **тільки одну папку за запуск**. Перший запуск завжди рекомендується робити в режимі попереднього перегляду **на копії** каталогу і файлів. Інструмент не здогадується про порядок ПІБ за словником: джерелом є окремі поля `authors.first_name`, `authors.middle_name`, `authors.last_name`, підтверджені зв’язками `book_authors` для кожної книги у папці.

## Обмеження та захист

- Необхідні коректні, відповідні фізичній папці `collection_root` у таблицях `books` і `book_artifacts`, без застарілих шляхів.
- Не допускаються колізії цільових папок (у тому числі без урахування регістру), символічні посилання, відсутні або некаталогізовані файли, неоднозначні автори, непідтверджені зв’язки автора та книги, нестандартне `archive_name` в артефакті.
- Обробляється **ціла папка**, а не один запис. Якщо один ZIP відповідає кільком книгам, всі їхні записи в обох таблицях повинні бути узгоджені.
- Перед зміною обчислюються SHA-256 файлів, створюється узгоджена SQLite-резервна копія, а потім журнал відновлення. Після перейменування суми перевіряються повторно, а SQL оновлюється однією транзакцією.
- Якщо збій відбувся між перейменуванням папки й фіксацією SQL, у журналі залишається `*.pending.json`. Новий ремонт блокується до відновлення; `--recover` перевіряє файли й SQLite та завершує або відкочує незавершену дію без перезапису чужих файлів.
- Цей інструмент **не виконує масового автоматичного ремонту** та не змінює назви папок, для яких немає достовірного джерела порядку ПІБ.

## Порядок використання у Windows

1. Повністю закрийте MyHomeLib та інші застосунки, які використовують SQLite-файл. Зробіть додаткову резервну копію **всієї бібліотеки** або тестової колекції. Не використовуйте звичайне копіювання тільки `Flib.db`, якщо існує активний файл `Flib.db-wal` — потрібна узгоджена резервна копія SQLite.
2. Визначте справжню кореневу папку колекції, а не папку, в якій випадково розташований `Flib.db`.
3. Запустіть **тільки попередній перегляд**; приклад (шляхи необхідно замінити своїми):

```powershell
py -3 tools\repair-author-folder.py --catalog "C:\Backup\Flib.db" --root "D:\Другие" --source "Алёна Васильева"
```

4. Якщо попередній перегляд підтвердить правильність назви та посилань і ви спочатку перевірили роботу **на копії**, можна виконати разову дію:

```powershell
py -3 tools\repair-author-folder.py --catalog "C:\Backup\Flib.db" --root "D:\Другие" --source "Алёна Васильева" --apply --offline-confirmed --backup "C:\Backup\Flib-before-rename-001.db" --journal-dir "C:\Backup\author-repair-journals"
```

**УВАГА:** у другому прикладі `--catalog` — база, яку програма справді змінюватиме. Якщо це лише копія, робоча база MyHomeLib не оновиться. Для реальної колекції потрібні зупинений застосунок, фактична база, перевірені шляхи й окремий бекап. При невідповідності кореня інструмент зупиниться.

5. Якщо після збою залишився `*.pending.json`, **не запускайте нову зміну**, поки не виконали:

```powershell
py -3 tools\repair-author-folder.py --catalog "C:\Backup\Flib.db" --root "D:\Другие" --recover --offline-confirmed --journal-dir "C:\Backup\author-repair-journals"
```

Якщо `--recover` повідомив про неоднозначний стан, не переміщуйте файли вручну: збережіть папку, журнал і копію бази для аналізу.

## Не доведено

Тести виконані на синтетичній SQLite-базі та локальній файловій системі. Результати не доводять сумісності з вашою `D:\Flib\Flib.db`, усіма варіантами старих колекцій або реальними Windows-архівами. До підтвердження роботи на копії, **не запускайте `--apply` на оригіналі всієї бібліотеки**.

## Додатковий захист від одночасних запусків (етап 10)

- Операції `--apply` і `--recover` використовують міжпроцесні блокування **за журналом і за фізичним SQLite-каталогом**. Навіть якщо для однієї SQLite-бази вказати різні папки журналів, другий ремонт буде відхилено, поки працює перший.
- Блокування автоматично звільняється операційною системою після завершення чи аварійного припинення процесу. Постійний маленький `.lock`-файл **не є незавершеним ремонтом**: не видаляйте його за працюючої утиліти. В Windows блокування використовує системні byte-range locks, а в Linux — `flock`.
- Блокування координує **лише інструменти ремонту**, а не інші застосунки. `--offline-confirmed` є підтвердженням користувача, не автоматичною перевіркою того, що MyHomeLib, сторонній редактор SQLite або файловий синхронізатор закриті. Вимога повністю закрити їх залишається обов'язковою.
- Якщо під час створення резервної копії інше SQLite-з'єднання змінить каталог, інструмент відмовиться від перейменування. Це додатковий захист, а не заміна офлайн-режиму чи незалежної резервної копії.
- Нова перевірка Windows-блокувань ще потребує виконання на Windows: тести міжпроцесного блокування виконані в Linux; перед реальними змінами перевірте поведінку на копії бібліотеки.

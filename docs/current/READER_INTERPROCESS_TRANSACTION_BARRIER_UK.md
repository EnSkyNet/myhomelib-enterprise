# Reader: міжпроцесна узгодженість позицій — V9

## Обсяг

`ReaderProgressTransactionGuard` серіалізує чотири шляхи в `NewReaderPersistenceService`:
`savePosition`, `loadPosition` (з відновленням), `saveAudioPosition` та
`loadAudioPosition` (з відновленням). Замок береться до отримання актуальної
позиції з SQLite, а звільняється після повернення з транзакції, запису до
recovery-журналу та умовного підтвердження. Порядок замків завжди такий:
`positionLock` у JVM → міжпроцесний `ReaderProgressTransactionGuard` →
`LibraryOperationCoordinator` → SQLite / `ReaderRecoveryFileGuard`.

**Інваріант:** два екземпляри Reader, які використовують ці самі каталоги
AppPaths та цю версію застосунку, не виконують одночасно read-modify-save
для однієї книги; колізії однобайтового SHA-256-страйпа можуть лише
серіалізувати *додаткові* книги, але не послаблюють захист.

Lock-файли зберігаються у `AppPaths.dataDir()/reader-progress-transactions`
(max 256), є стабільними та **не видаляються** під час звичайної роботи.
Видалення lock-файлу, поки інший процес його використовує, може розділити
домен блокування. Каталоги й файли перевіряються проти symlink/reparse;
тайм-аут 8 секунд, відмова не призводить до початку запису. Старші процеси,
які не користуються цим замком, **не входять до цієї гарантії**.

## Чого гарантія не охоплює

- Синхронізатори, import/export, зовнішні SQL-клієнти та старі версії Reader
  можуть змінювати `reading_progress`, оминаючи бар'єр. Для них потрібна
  окрема ревізія SQLite/compare-and-swap або єдиний writer колекції.
- OS file lock не є заміною транзакції SQLite, фізичного `fsync` чи бекапу.
- Роботу замків і NTFS/SMB під Windows не перевірено в Linux-середовищі.
- Повну Java/Spring/Maven інтеграцію не виконано через неповний офлайновий кеш.

## Ручний тест приймання на копії бібліотеки

1. Зробити резервну копію SQLite, файлів і recovery-журналів у **нову** теку.
2. Увімкнути два Reader-процеси V9, прив'язані до однієї тестової колекції.
3. Затримати процес A після читання поточного стану, до коміту;
   процес B має очікувати звільнення замка й тільки потім перечитати SQLite.
4. Перевірити text/audio anchors та `PRAGMA integrity_check`, `foreign_key_check`.
5. Симулювати lock contention >8 секунд: жодна позиція не має частково
   оновитися, автозбереження повертає `false` і може повторитися.
6. Завершити процес між journal prepare / SQLite commit / acknowledge;
   перевірити відновлення після наступного запуску та збереження журналу
   у випадку конфлікту.
7. Додатково перевірити SMB/NTFS, режим роботи без права запису,
   антивірус, long paths і синхронізатор, який не бере Reader lock.

## Відтворювана автономна перевірка

```bash
python tools/reader-progress-transaction-jdk-smoke.py
python -m unittest discover -s tools/tests -p 'test_*.py' -v
```

Для production-допуску необхідна **повна** Maven `clean verify` з JUnit,
інтеграційне приймання через Spring/Flyway та Windows-тести на копії.

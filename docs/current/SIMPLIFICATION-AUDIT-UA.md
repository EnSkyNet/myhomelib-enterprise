# MyHomeLib R18 — аудит спрощення й наближення до релізу (V32 → V33)

**Дата:** 18.10.2026. **База:** точний вихідний ZIP V32. **Обсяг:** читання архітектури, Maven-реактора, критичного коду Apply/Undo, запуску, пакування, історичних документів; контрольні статичні та автоматичні перевірки. **Не проводилось:** вимірювань тривалого Windows/UI-навантаження, інструментального профілювання робочої бібліотеки, Windows NTFS/UNC/DPAPI, змін реальної `Flib.db`.

## 1. Висновок

MyHomeLib — уже **великий модульний десктопний моноліт**, а не невелика утиліта. 21 Maven-проєкт — це не 21 незалежна служба; модулі забезпечують межі залежностей. Саме число модулів не є достатньою причиною переписувати архітектуру. Натомість великі класи, складні контракти організатора та історичні описи ускладнюють щоденні зміни. Відкладати реліз заради нескінченних варіацій теоретичних гонок недоцільно.

**Новий принцип:** спочатку підтвердити реальну проблему, виміряти її вплив, потім виконати найменшу безпечну зміну з тестом. Не переписувати кілька сотень тисяч рядків із нуля; це створить значно більше неперевірених регресій, ніж прибере.

## 3. Результати аудиту за напрямами

### Залишити без зміни контракту

- SQLite-транзакції, Flyway/WAL, інваріанти ідентичності колекції та CAS при зміні даних.
- Схему «план → staging → SHA-256 → публікація → каталог → відкат/ручна перевірка» для фізичного переміщення книжок.
- Запобігання перезапису чужих файлів, захист шляхів і символьних посилань, read-only сценарії для реальної бібліотеки.
- Відновлення позиції Reader та відхилення застарілих записувачів.
- Плагінові/OPDS/MCP-контракти, якщо функціональність підтримується, але запуск необов'язкових сервісів має залишатися явним/налаштовуваним.

Причина: їх видалення може привести до втрати даних, а не до відчутного прискорення старту.

### Спростити зараз (малий ризик, зрозумілий виграш)

1. **Єдина копія логіки переходу стану журналу.** Раніше Apply та Undo вручну конструювали 22-польовий `OrganizationJournalItem` при зміні стану. В V33 використовується `withOutcome(...)`: збереження всіх полів і правил fallback SHA-256 описане один раз; додано тести незмінності метаданих.
2. **Коротка актуальна стартова документація.** Замість застарілих цифр тестів та старого checkpoint у README — реальні модулі, одна схема команд, явні release gates.
3. **Швидкий локальний цикл без тестів, але з обов'язковим повним релізним прогоном.** `build.sh --fast` / `build.ps1 --fast` працюють лише з desktop dependency graph. Без аргументу виконується як і раніше `clean verify` всіх модулів. Не використовувати `--fast` як релізний доказ.
4. **Не засмічувати runtime технічними матеріалами.** `docs/history` і тести вже не завантажуються під час роботи UI. Їх можна винести в окремий history/evidence artifact пізніше, але лише після узгодження source-integrity/CI policy, бо кілька перевірок наразі посилаються на історичні файли.

## 4. Чого робити не треба

- Не видаляти SQL/CAS/recovery заради скорочення кількості рядків.
- Не зливати Domain/Application/Infrastructure/UI в один модуль: це зруйнує корисні межі та незалежне тестування.
- Не переписувати JavaFX застосунок із нуля. Це неконтрольована втрата наявних функцій без вимірюваного виграшу.
- Не видаляти EPUBCheck: він є реальною частиною пакета. Натомість **виміряти**, скільки часу й пам'яті він використовує саме в потрібних сценаріях.
- Не трактувати успішний Linux/JUnit як підтвердження Windows/NTFS/DPAPI.
- Не маркувати пропущені тести як виконані.

## 5. Release acceptance: короткі чіткі ворота

1. На Windows x64 інсталювати та запустити створений артефакт; окремо перевірити portable режим, каталоги з кирилицею та UNC/NTFS.
2. На незалежній **копії** бібліотеки/SQLite пройти: імпорт INPX, пошук, відкриття FB2/EPUB, збереження позиції, організатор `MOVE/COPY`, скасування, Undo та перезапуск.
3. Зібрати контрольні цифри: cold/warm startup, RAM idle/Reader/import, пошук P50/P95, час 100/1000 копіювань, вікно `ORGANIZER_IO_STALL`, масштабне навантаження каталогу.
4. Один релізний `clean verify` всіх модулів + 101 Python-регресія + перевірка ZIP/PATCH/SHA-256 та native packaging.
5. Жодних непояснених P0/P1 втрат даних, зависань, недоступних UI-функцій; мати шлях відновлення з backup.

**Поточне рішення:** залишатися Linux release candidate до виконання Windows acceptance. Цей аудит не дає дозволу змінювати реальну `Flib.db` чи бібліотеку.

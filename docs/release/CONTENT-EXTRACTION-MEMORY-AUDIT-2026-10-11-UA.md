# MyHomeLib R18 — аудит коду та використання пам’яті

Оновлено **2026-10-12**. Основа — MyHomeLib Enterprise 8.0.0 R18 із попередніми виправленнями extraction та заголовків EPUB. Цей пакет додає обмеження пам’яті метаданих EPUB, своєчасне скасування їх розбору та надійні перевірки визначення каталогу запуску.

У виконаному 2026-10-11 цільовому Maven-прогоні пройдено **53 тести: 0 failures, 0 errors, 0 skipped**. Перед пакуванням 2026-10-12 повторно виконано архітектурну перевірку й `build-check-v7.py` — **PASS**. Повний root `clean verify` цього набору змін не виконано.

## Нові виправлення

### Метадані EPUB

До цієї зміни `container.xml` та OPF використовували загальний ліміт ZIP-entry — 512 MiB. Ліміт основного тексту й заголовків не обмежував списки manifest/spine, які накопичувалися до читання розділів. Вхід із багатьма повторними або нерозв’язними посиланнями міг створювати великі колекції без корисного тексту.

У `EpubContentExtractor` додано:

| Об’єкт | Межа | Поведінка |
| --- | ---: | --- |
| `container.xml` | 8 388 608 байтів | Перевірка заявленого розпакованого розміру до парсера та обмежений потік під час читання. |
| OPF | 8 388 608 байтів | Та сама незалежна межа; це розмір метаданих, а не всього EPUB. |
| Manifest | 100 000 декларацій `item` | Враховуються також повторні ID та непридатні декларації. |
| Spine | 100 000 декларацій `itemref` | Враховуються також посилання без відповідного розділу. |

Межі включні. Перевищення повертає `FAILED` без часткового `ExtractedContent`. Це ресурсна політика застосунку: раніше прийнятий EPUB із метаданими понад ці межі тепер буде відхилено. Стиснення ZIP не дозволяє обійти перевірку розпакованого розміру.

Перевірки скасування тепер є перед індексацією ZIP, між ZIP-записами, перед читанням метаданих і між подіями їх XML. Скасування після завершення копіювання EPUB повертає `CANCELLED` до розбору метаданих, зокрема коли XML некоректний. Переривання всередині одного виклику XML-парсера не гарантується; розмір метаданих окремо обмежено.

Додатково прибрано повторне копіювання map manifest і list spine при створенні приватного `EpubPackage`. Власні колекції передаються через незмінювані обгортки й надалі не модифікуються. Це усуває проміжні копії контейнерів; нового відсотка економії RAM або виміряного RSS для цього патча не заявляється.

### Перевірка каталогу запуску

`AppPathsLaunchDirTest` раніше вимагав, щоб операційна система завжди надавала командний шлях поточного процесу, хоча production-код уже підтримував відсутність цих даних. Через порожній `Optional` тест завершувався `NoSuchElementException` ще до перевірки потрібної поведінки.

Тест native launcher тепер задає відомий шлях через Mockito й перевіряє його пріоритет над `user.dir`. Додано два окремі випадки: недоступні command metadata та відмова доступу через `SecurityException`. Обидва перевіряють передбачений fallback на `user.dir`. Разом у наборі 5 тестів. Production-код `AppPaths` не змінено; це перевірка контракту, а не підтвердження реального Windows launcher.

## Що залишається непідтвердженим

Повний root `clean verify` після цих змін не виконано. У ранішому root-прогоні тест дерева дочірніх процесів не працював через відсутність видимості `ProcessHandle.descendants()` у середовищі. Він залишається активним і незміненим. Помилку передумови `AppPathsLaunchDirTest` усунено та його 5 випадків перевірено окремо; це саме по собі не підтверджує завершення всього reactor.

Потрібен root-прогін без виключень у повному desktop-середовищі. Реальний Windows launcher, пакування інсталятора, пристрої, тривала робота застосунку й RSS повного desktop-процесу цим прогоном не підтверджуються. Історичні `21/21 BUILD SUCCESS` у старих документах стосуються попередніх версій.

## Як повторити перевірки

З кореня проєкту, з JDK 21, Maven та доступними залежностями:

```bash
mvn -B -ntp -Pproduction -pl myhomelib-bootstrap -am \
  -Dtest=EpubPackageBudgetTest,EpubTitleBudgetTest,ContentDocumentBuilderTest,ContentExtractionResourceRegressionTest,ContentExtractorContractTest,ExtractedContentTest,TextStreamDecoderTest,LuceneContentIndexServiceIntegrationTest,AppPathsLaunchDirTest \
  -Dsurefire.failIfNoSpecifiedTests=false test

python3 tools/architecture-check.py
python3 tools/build-check-v7.py
```

Для offline-запуску додайте `-o -Dmaven.repo.local=/path/to/repository`. Linux desktop-тестам потрібні відповідні native-бібліотеки та дисплей/Xvfb. Повна перевірка на належно підготовленому комп’ютері:

```bash
mvn -Pproduction clean verify
```

## Попередні оптимізації збережено

Пакет включає попереднє усунення зайвих копій тексту книги, потокову нормалізацію FB2/EPUB/TXT, читання TXT блоками, виправлення UTF-8 на межі проби, правильні роздільники EPUB, ліміти тексту й абзаців та захист заголовків. Межі: 67 108 864 одиниці UTF-16 тексту, 250 000 непорожніх абзаців, 65 536 одиниць UTF-16 на заголовок і 1 048 576 сумарно для заголовків.

Раніше виконана окрема стрес-проба заголовків при `-Xmx64m` дала `OutOfMemoryError` до їх захисту та контрольований `FAILED` після нього. Її запис і обмеження висновків залишаються в `epub-title-budget-evidence/`. Це не нове вимірювання RAM для метаданих. Загальні витрати пам’яті не є константними: підсумковий текст і структура книги залишаються в heap.

Схема повнотекстового індексу залишається **2**. Якщо оновлення виконується зі schema 1, потрібна одноразова перебудова індексу вмісту. Для вже перебудованого schema 2 новий перехід схеми не потрібен. SQLite, індекс метаданих каталогу, залежності й production heap-параметри цього продовження не змінено.

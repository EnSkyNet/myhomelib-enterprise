# MyHomeLib 8.0.0 R18 — відновлення EPUB-конвертації та впорядкування книг

Дата: 15 жовтня 2026 року.

## Підтверджена причина за myhomelib(1).log

- 10:22–10:24: `fbc.exe` успішно перетворив FB2 на EPUB (exitCode=0), EPUBCheck і перевірка читачем успішні. `SafeFilePublication.java:102` впав на `Files.createLink()` під час фінального збереження до `D:\Flib`.
- 10:34: підготовлено 14 078 дій упорядкування; перший файл скопійовано, SHA-256 перевірено, але `OrganizerTargetPublisher.java:65` впав на `Files.createLink()` у каталозі на диску `D:`.
- Обидві помилки: `java.nio.file.FileSystemException: ... Неверная функция`. Це відмова файлової системи виконати операцію hard link, а не збій `fbc.exe` чи копіювання.

## Виправлення

1. У `myhomelib-shared/.../SafeFilePrimitives.java` додано спільний `publishFreshNoReplace`: спершу швидка атомарна публікація через hard link; якщо файлова система повідомляє, що операція не підтримується, резервна публікація через `Files.copy` **без** `REPLACE_EXISTING`.
2. `myhomelib-application/.../SafeFilePublication.java` тепер використовує цю функцію замість прямого `Files.createLink`.
3. `myhomelib-library-organizer/.../OrganizerTargetPublisher.java` використовує ту саму функцію. SHA-256 цільових файлів перевіряється перед оновленням каталогу та видаленням старого файла.
4. Додано тест `SafeFilePrimitivesPublicationFallbackTest`: емулює повідомлення `Неверная функция`, перевіряє наявний файл, помилки доступу та одночасні публікації.
5. Діагностика `FILE_PUBLICATION_HARDLINK_UNSUPPORTED`: перше повідомлення, а далі кожна тисячна резервна публікація, щоб 14 тис. файлів не засмічували журнал.

## Перевірки

- Java 21: окремо скомпільовано всі 6 класів публікації та захисту шляхів — успішно.
- Локальна Java smoke-програма: успішні публікації після конвертації та для організатора; SHA-256 перевіряється.
- Емуляція Windows ERROR_INVALID_FUNCTION у Java 21: успішний резервний шлях; 80 конкурентних спроб запису в однаковий файл, лише один переможець у кожній спробі; відсутній перезапис чужого файла.
- `python tools/static_release_check.py`: PASS (XML/FXML/SQLite/CI).

**Обмеження:** у середовищі перевірки немає Maven CLI і Windows-файлової системи, тому повний `mvn clean verify` та інтеграційні випробування на реальному диску `D:` не проводилися. Збірку `.exe` не створено: цей пакет — виправлений *вихідний код*.

## Важливі правила цілісності

- Якщо hard link доступний, цільове ім’я стає видимим лише після завершення попередньої перевірки.
- На томах без hard link резервна операція `Files.copy` не перезаписує існуючих файлів і зберігає оригінал, але щойно створений вихідний файл може бути тимчасово видимим до завершення копіювання. Каталог книги оновлюється лише після завершення SHA-256 перевірки.
- Якщо резервне копіювання перерветься через відмову диска, може залишитися неповний *новий* цільовий файл. Власний оригінал не видаляється; перед повторною спробою перевіряйте й окремо прибирайте лише такий незавершений цільовий файл після резервного копіювання.
- Інші місця використання `Files.createLink()` поза EPUB та організатором не змінювалися, щоб обмежити ризик регресії.

## Рекомендована приймальна перевірка у Windows

1. Зробіть резервну копію бібліотеки та БД; не запускайте організатор на всіх 14 078 книгах без тесту.
2. Зберіть застосунок із поточного архіву згідно з README (Java 21 та Maven).
3. Конвертуйте один FB2 на той самий диск `D:` у EPUB; переконайтеся, що EPUB відкривається, а в логах є `FILE_PUBLICATION_HARDLINK_UNSUPPORTED` і успішне завершення конвертації.
4. На копії каталогу впорядкуйте 2–5 книг у режимі MOVE_AND_RENAME; переконайтеся, що вихідні/кінцеві SHA-256 однакові, метадані оновлені, а початкові файли видалені **лише** після підтвердження результату.
5. Перевірте переривання/скасування операції, повторний запуск і конфлікт імені. Лише тоді запускайте весь план на 14 078 книг.

# Iteration 12 — Support Bundle privacy and external-reader temp lifecycle\n\nDate: 2026-09-06\nBaseline: Iteration 11 (`myhomelib-enterprise-7.1.0-rc3-iter11-transactional-edit-domain-immutability.zip`)\nScope: MHL-032 + MHL-038\n\n## 1. Backlog mapping\n\n### MHL-032 — Sanitize Support Bundle\n\nAcceptance addressed:\n\n1. Synthetic secrets, paths, URLs and private diagnostic values are redacted.\n2. Log file names and existing size limits remain observable/preserved; oversized logs are excluded.\n3. The user sees bundle composition and can include/exclude logs, thread dump and release documents before export.\n4. Application version is resolved from packaged runtime/build metadata instead of hard-coded `7.1.0`.\n\n### MHL-038 — Manage lifecycle of materialized external-reader files\n\nAcceptance addressed:\n\n1. Pre-existing cache files are treated as crash leftovers and removed on the next startup.\n2. The cache has per-file, total-size and age bounds.\n3. A tracked external process retains an active lease until `Process.onExit`, so its file is not deleted prematurely.\n4. Untracked `Desktop.open` materializations are deliberately kept until next startup, which provides crash/session recovery without risking deletion while the external reader still uses the file.\n\n## 2. Implementation\n\n### Support bundle\n\n- Added `SupportBundleSanitizer` with line-by-line redaction for secrets, URLs, e-mail addresses, private book/author fields and user/application paths.\n- `SupportBundleService` sanitizes environment, settings, thread dumps, release documents and logs before writing them to ZIP. Raw log copying is no longer used.\n- Exact `dataDir` and `launchDir` are represented by stable aliases in `environment.txt`.\n- Absolute path settings are redacted as a complete value. This was strengthened after a privacy regression test showed that prefix-only pseudonymization could still expose a collection-name/path suffix.\n- Added `SupportBundleOptions` and `SupportBundlePreview`; the settings dialog exposes the bundle composition and optional categories before saving.\n- Version resolution uses `jpackage.app-version`, package manifest metadata or Maven `pom.properties`, with `development` only as a non-packaged fallback.\n- Existing log size controls remain: 10 MiB per log file and 30 MiB total source logs.\n\n### External-reader cache\n\n- Added application-level `ExternalReaderMaterializationCache`.\n- Materialized names are opaque UUID-based names and do not embed book titles.\n- Default total cache limit is 1 GiB, with the archive-safety single-file limit and a 24-hour inactive TTL.\n- Startup removes leftovers from a previous process/session before accepting new materializations.\n- Active leases are excluded from TTL/size eviction.\n- `RunBookActionUseCase` adopts temporary resolved content into the managed cache.\n- `BookActionExecutionService` exposes the detached `Process` to a lifecycle observer; the lease survives until that process exits.\n- `ExternalBookLauncher` uses the same cache. For command execution it tracks the process; for `Desktop.open` it preserves the lease until the next startup because Java Desktop does not provide a portable child-process handle.\n- The previous `deleteOnExit` behavior was removed from these paths.\n- `retainUntil(Process)` compensates its extra hold if `Process.onExit()` callback registration itself throws, avoiding a leaked active lease.\n\n## 3. Security/lifecycle rationale\n\nSupport bundles are treated as potentially shareable diagnostics, therefore redaction is performed before bytes enter the ZIP rather than after archive creation. Whole-value redaction is used for absolute setting paths because replacing only a root prefix can still reveal collection/book names in the suffix.\n\nFor external readers, deletion correctness is intentionally asymmetric: deleting too late leaves a bounded, next-startup-cleaned privacy artifact; deleting too early can corrupt the user's active reading session. Therefore tracked processes are authoritative, while untracked Desktop launches use conservative next-startup cleanup.\n\n## 6. Known limitation\n\n`Desktop.open` does not expose a portable `Process` handle, so MyHomeLib cannot reliably know when the external application has finished reading the file. Such a materialization is kept through the current session and removed at the next application startup. This is deliberate and covered by lifecycle tests.\n
